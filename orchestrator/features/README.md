# BDD-харнесс оркестратора (godog) — тикет 11.2

> Реализует ТЗ §127 «Весь функционал покрыт автоматическими тестами» на
> уровне приёмочных Gherkin-сценариев из `docs/User_stories_Gherkin.md`.
> `docs/User_stories_Gherkin.md` остаётся единственным источником текста
> сценариев — файлы в этом каталоге лишь переносят его в исполняемый формат
> `.feature`, текст не меняется (кроме явно помеченных фрагментов, где
> сохранение оригинала было физически невозможно, например строк со
> служебными комментариями к тегам).

## Что это и как устроено

- **`.feature`-файлы** (этот каталог) — Gherkin-сценарии на русском
  (`# language: ru`, cucumber/gherkin поддерживает русские ключевые слова
  `Функция`/`Сценарий`/`Структура сценария`/`Дано`/`Когда`/`Тогда`/`И`/`Но`
  из коробки). Один файл на раздел `docs/User_stories_Gherkin.md` (`01_…`
  … `10_…`, нумерация соответствует §1–§10 документа).
- **Степы** — `orchestrator/internal/bddsteps/*_test.go` (build-тег `bdd`,
  как `//go:build integration` у `*_integration_test.go`: обычный
  `go build`/`go test`/`go vet`/`golangci-lint` их не видит без явного тега,
  поэтому `make lint`/`make test` не требуют Docker). Степы поднимают ТОТ ЖЕ
  `api.NewRouter`, что и прод/остальные интеграционные тесты, поверх
  настоящего Postgres в testcontainers-go (тот же паттерн, что
  `orchestrator/internal/api/*_integration_test.go`) — HTTP/WS вызовы в
  степах бьют в реальный код оркестратора, не в моки.
- **Запуск**: `make bdd` (см. `Makefile`) → `go test -tags=bdd
  ./orchestrator/internal/bddsteps/... -run TestFeatures`.

## Что покрыто

`§1` Регистрация и доступ, `§2` Интеграции и машины (кроме install-скрипта),
`§4` Постановка задачи, `§5` Q&A и согласование (кроме allowlist-решения
агента), `§6` Уведомления (web WebSocket), `§7` Завершение задачи, `§8`
Отмена (уровень «команда отправлена оркестратором»), `§9` частично (только
«Машина пропала надолго» — целиком на Postgres), `§10` История.

## Что НЕ покрыто и почему (теги)

Сценарии, которые заведомо не могут быть проверены в этом харнессе,
помечены тегом и НЕ входят в набор по умолчанию (см. `GODOG_TAGS` ниже).
Каждый такой сценарий — не забытый, а сознательно вынесенный: рядом с ним в
`.feature`-файле есть комментарий с обоснованием и, где применимо, ссылкой
на альтернативное покрытие.

| Тег | Значение | Где ещё покрыто |
|---|---|---|
| `@manual` | Не HTTP/WS-поверхность оркестратора (install-скрипт, provisioning реальной ОС, §3) | `install/test-install.sh` (CI-джоба `agent-install-test`, тикет 4.2); `agent-service-test` (тикет 4.4) |
| `@redpanda` | Требует настоящий брокер Redpanda (мост оркестратор↔агент, presence по heartbeat, оффлайн-догон) — тестовый Redpanda-образ недоступен в текущей CI-песочнице (см. ниже) | `orchestrator/internal/bridge/bridge_integration_test.go`, `orchestrator/internal/api/presence_integration_test.go`, `orchestrator/internal/api/tasks_integration_test.go` (все — тег `integration`, реальная Redpanda); дальнейшее углубление — тикет 11.3 |
| `@wip` | Требует функциональности вне текущего объёма эпика (allowlist — agent-side; safe-stop при отмене — тикет 8.5, ещё не реализован; Telegram-доставка — отдельный сервис `/bot`) | agent-side покрыто юнит-тестами `agent/internal/provider/claudecode`; остальное — будущими тикетами |

### Про `@redpanda` и сеть

При написании этого харнесса `docker pull redpandadata/redpanda:...` в
текущей CI/дев-песочнице падал `403 Forbidden` (сетевой прокси окружения не
пропускает этот реестр), тогда как `postgres:16-alpine` тянется штатно —
поэтому решение архитектурно не заводить Redpanda в BDD-харнесс вообще,
а не пытаться поднимать её условно. Если в конкретном окружении (например,
GitHub-hosted раннер с обычным доступом в интернет) Redpanda тянется без
проблем, `@redpanda`-сценарии всё равно НЕ включаются по умолчанию — это
осознанное разделение ответственности с тикетом 11.3 (там же будет решение
про полноценный Redpanda-стенд для более глубоких сценариев очереди/FSM/
оффлайн), а не техническое ограничение сети.

## Как запускать

```bash
make bdd
```

Что это делает: поднимает один Postgres-контейнер (testcontainers-go) на всю
сессию, прогоняет миграции, затем перед КАЖДЫМ сценарием truncate всех
таблиц (изоляция между сценариями на общем контейнере — контейнер один,
чтобы не поднимать Postgres десятки раз, TRUNCATE — единицы миллисекунд).
Требуется Docker (как и `make test-integration`/CI-джоба `integration`).

По умолчанию исключены `@manual`, `@redpanda`, `@wip` (см. выше). Чтобы
переопределить фильтр тегов (например, локально прогнать `@redpanda`,
предварительно подняв доступ к Redpanda-образу):

```bash
GODOG_TAGS="~@manual && ~@wip" make bdd   # включить @redpanda-сценарии
GODOG_TAGS="@qa"               make bdd   # прогнать только сценарии с тегом @qa (если есть)
```

## Как добавить новый сценарий

1. Сценарий уже должен существовать в `docs/User_stories_Gherkin.md` (это
   источник правды — новые пользовательские сценарии сначала описываются
   там, БИЗНЕС-текстом, см. AGENTS.md §6 «Трассируемость»). Если сценария
   там нет — сначала дополни этот документ, отдельным изменением.
2. Скопируй его текст без изменений в подходящий `NN_*.feature` файл (или
   заведи новый файл, если это новый раздел §).
3. Если сценарий проверяет уже реализованную функциональность —
   допиши/переиспользуй степы в `orchestrator/internal/bddsteps/steps_*_test.go`
   (по одному файлу на раздел, как и `.feature`-файлы). Регистрируй новые
   степы в соответствующей `register*Steps` функции.
4. Если сценарий зависит от ещё не реализованной функциональности — пометь
   его тегом `@wip` с комментарием-обоснованием (по образцу существующих) и
   НЕ добавляй под него степы (undefined step в godog не ломает сборку, но
   и не должен маскировать «мы забыли», поэтому обоснование обязательно).
5. Прогони `make bdd` локально и убедись, что новый сценарий подхватился
   (godog печатает список сценариев с результатом каждого).

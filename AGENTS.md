# AGENTS.md

> Устав работы в этом репозитории — для людей и для кодовых агентов (Claude Code, Cursor и т.п.).
> Главный принцип: **код без актуальной документации считается незавершённым.** Документация — часть Definition of Done, а не отдельная задача «потом».

---

## 0. TL;DR для агента/разработчика
Прежде чем открыть PR, проверь:
1. Каждый затронутый пакет/модуль имеет актуальное **описание «что и зачем»** (тех + бизнес).
2. Каждый публичный символ (экспортируемая функция, тип, эндпоинт) **задокументирован**.
3. Если менял поведение → обновил соответствующие доки **в этом же PR** (см. §4 «правило одного PR»).
4. Если принял архитектурное решение → добавил **ADR** (§5).
5. Если менял API → обновил `api/openapi.yaml` и перегенерировал клиентов (`make generate`).
6. Прошли `make lint test` и проверка документации (`make docs-check`).

---

## 1. Что считается документацией здесь

Делим на два слоя, оба обязательны:

- **Техническая** — *как это работает*: сигнатуры, контракты, инварианты, формат сообщений в шине, схемы БД, последовательность переходов FSM.
- **Бизнесовая** — *зачем это нужно*: какую пользовательскую ценность и какое требование ТЗ закрывает код. Возле нетривиальной логики — комментарий с **trace-ссылкой** на требование (`FR E2`, `Gherkin §7`) и причиной решения.

> Правило: если из кода не очевидно, **почему** так, а не иначе — это бизнес-комментарий, и он обязателен. Если не очевидно **что** делает — это тех-комментарий.

---

## 2. Где живёт документация

| Тип | Где | Чем поддерживается актуальность |
|---|---|---|
| Назначение пакета (Go) | `doc.go` или комментарий пакета | ревью + `make docs-check` |
| Публичные символы (Go) | godoc-комментарии над символом | `golangci-lint` (`revive`/`godot`) |
| API | `api/openapi.yaml` (источник правды) | `make generate` + CI-diff |
| Схема БД | комментарии в миграциях + `COMMENT ON` в SQL | ревью |
| Архитектурные решения | `docs/adr/NNNN-*.md` | обязательны при изменении архитектуры |
| Бизнес-контекст компонента | `README.md` в каждом сервисе (`/orchestrator`, `/bot`, `/agent`, `/web`) | правило одного PR (§4) |
| Протокол шины/сообщений | `docs/protocol.md` | при изменении топиков/сообщений |
| Глоссарий | `docs/glossary.md` (из §4 бизнес-ТЗ) | при появлении новых терминов |

## 3. Стандарты по языкам

### Go (оркестратор, бот, агент)
- Каждый пакет: комментарий пакета или `doc.go`, начинающийся с `// Package xxx ...`, с разделами **Назначение** (бизнес) и **Как устроено** (тех).
- Каждый экспортируемый тип/функция/метод — godoc-комментарий, начинающийся с имени символа.
- Нетривиальная бизнес-логика — построчный комментарий с trace-ссылкой:
  ```go
  // «Агент сообщил о завершении» НЕ закрывает задачу — закрывает только
  // явное подтверждение пользователя. См. FR E2, Gherkin §7.
  func (t *Task) ReportCompletedByAgent() error { ... }
  ```
- Включить линтеры документации: `revive` (exported), `godot` (точки), `godoclint`.

### SQL (миграции)
- Каждая таблица и нетривиальная колонка — `COMMENT ON TABLE/COLUMN ... IS '...'` с бизнес-смыслом.
- В шапке миграции — что и зачем меняем, какое требование закрываем.

### TypeScript / React (web)
- Каждый компонент/хук — JSDoc-блок: назначение + к какому экрану/сценарию относится.
- Типы API не пишем руками — генерим из `openapi.yaml`.

### OpenAPI
- Каждый эндпоинт: `summary`, `description` (вкл. бизнес-смысл и trace-ссылку), описанные коды ответов и ошибки.

## 4. Правило одного PR (главное)
**Изменение поведения и изменение его документации идут в одном и том же PR.**
- Поменял контракт эндпоинта → правишь `openapi.yaml` тут же.
- Поменял переход FSM → правишь `docs/` по жизненному циклу и комментарии тут же.
- Поменял формат сообщения в шине → правишь `docs/protocol.md` тут же.

PR, который меняет поведение, но не трогает доки, ревьюер **отклоняет** (если только в описании PR явно не обосновано, что доки не затронуты).

---

## 5. Архитектурные решения (ADR)
Любое значимое решение (выбор библиотеки, формат протокола, схема топиков, модель auth) фиксируется коротким ADR в `docs/adr/NNNN-title.md` по шаблону: **Контекст → Решение → Альтернативы → Последствия**. Базовые решения уже описаны в `docs/01_tech_stack_and_architecture.md` — новые добавляем туда же ссылками.

---

## 6. Трассируемость (бизнес ↔ код ↔ тест)
Связь «требование → код → тест» должна быть восстановима:
- В коде — trace-комментарии (`FR …`, `Gherkin §…`).
- В тестах — имя/тег теста ссылается на сценарий (godog .feature-файлы прямо используют Gherkin из ТЗ).
- В PR — в описании указываются закрываемые ID задач из `docs/02_mvp_backlog.md`.

## 7. Сборка, тесты, проверки (команды)
```bash
make tools        # установить sqlc, goose, oapi-codegen, golangci-lint, goreleaser
make generate     # сгенерировать код из openapi.yaml и sqlc-запросов
make lint         # golangci-lint (вкл. линтеры документации)
make test         # юнит + интеграционные (testcontainers: Postgres+Redpanda)
make bdd          # прогон Gherkin-сценариев (godog)
make docs-check   # проверка: нет публичных символов без godoc; openapi не разошёлся с кодом
make run-local    # поднять всё в docker compose локально
```
CI блокирует мёрж, если падает любой из `lint / test / bdd / docs-check`.
Реализация — [`.github/workflows/ci.yml`](.github/workflows/ci.yml) (тикет 0.4):
те же `make`-цели плюс `build`, `generate-check`, `integration` (testcontainers) и
`web`-typecheck; path-фильтры по сервисам. Какие чек-раны включить в branch
protection — см. раздел «CI» в [`README.md`](README.md). golangci-lint в CI
фиксирован на `v2.5.0` (v2-схема `.golangci.yml`).

## 8. Чего НЕ делаем
- Не коммитим секреты (см. `docs/03_pre_dev_setup.md`). Только GitHub Secrets / `.env` на хосте.
- Не пишем фичи вне объёма MVP (см. §9 бизнес-ТЗ) без явного решения.
- Не оставляем `TODO` без трассировки задачи (`// TODO(#123): ...`).

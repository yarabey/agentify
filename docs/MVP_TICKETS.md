# MVP — Тикеты (полная детализация) и последовательность реализации

> Единый источник задач для разработки. Консолидирует и **заменяет** прежние `02_mvp_backlog.md` и `04_epic_details_tickets.md`.
> Стек зафиксирован (см. `01_tech_stack_and_architecture.md`): Go (оркестратор/бот/агент), React/PWA (web), PostgreSQL, Redpanda. Контракт — `openapi.yaml`. Схема БД — `migrations/`. FSM — `Жизненный цикл задачи.md`. Правила документации — `AGENTS.md`.
> **Никаких скелетов заранее нет** — каждый файл создаётся внутри своего тикета.

## Как читать тикет
```
#### <ID> — <Название> · <Размер> · deps: <ID,…>
- Эндпоинт(ы): из openapi.yaml (или «—»)
- Таблицы: из migrations/ (или «—»)
- Логика: пошагово, с правилами и кодами ошибок
- Приёмка: FR-коды + Gherkin §N «имена сценариев»
- Тесты: happy + edge
- Доки (DoD): что обновить по AGENTS.md
```
Размеры: **S** ≈ 0.5–1 д, **M** ≈ 1–3 д, **L** ≈ 3–5 д (для джуна; L при необходимости дробить).

**DoD по умолчанию для всех тикетов:** код + юнит/интеграционные тесты + (где есть Gherkin) godog-сценарий + обновлён `openapi.yaml` при изменении API + актуализированы доки по `AGENTS.md` (тех+бизнес, trace-комментарии, ADR при арх. решении — в том же PR) + зелёные `make lint test bdd docs-check`.

Статусы FSM: `created → queued → running ↔ waiting_user → awaiting_confirm → completed | failed | cancelled | stale`.

# Последовательность реализации

Жёсткий принцип из Roadmap: **сначала фундамент очереди** — без него остальное не имеет смысла. Внутри спринта тикеты можно параллелить между разработчиками с учётом `deps`.

| Спринт | Цель | Тикеты |
|---|---|---|
| **1. Фундамент** | Репо, CI, доступ, начало шины | 0.1 → 0.7, 1.1 → 1.7, 3.1, 3.2 |
| **2. Труба и машины** | Транспорт агента, статус, установка | 2.1 → 2.4, 3.3 → 3.6, 4.1 → 4.4 |
| **3. Задачи** | FSM, постановка, провайдер, начало Q&A | 5.1 → 5.8, 4.5 → 4.7, 6.1 → 6.2 |
| **4. Диалог, уведомления, Telegram** | Q&A, allowlist, уведомления, бот | 6.3 → 6.7, 7.1 → 7.4, 10.1 → 10.4 |
| **5. Завершение, web, сквозное** | Завершение/отмена/история, web, тесты | 2.5, 2.6, 8.1 → 8.9, 9.1 → 9.8, 11.1 → 11.5 |

**Критический путь:** `0.1 → 3.1 → 3.2 → 3.3 → 3.4 → 5.2 → 5.3 → 5.4 → 6.1 → 7.x → 8.x → 9.8`.
**Критерий выхода MVP** (тикет 9.8): задача из web и из Telegram → вопрос агента → уведомление → ответ → агент сообщил о завершении → подтверждение пользователя; оффлайн-машина догоняет (5.6); отмена останавливает безопасно (8.4/8.5).

# EPIC 1 — Доступ и аккаунты (FR A1–A4, Gherkin §1)

#### 1.1 — Схема auth · S · deps: 0.1
- Таблицы: `users`, `registration_tokens`, `refresh_tokens` (миграция 00001 — уже подготовлена).
- Логика: применить миграцию; sqlc-запросы CRUD.
- Тесты: миграция up/down проходит на testcontainer.

#### 1.2 — Регистрация по токену · M · deps: 1.1
- Эндпоинт: `POST /auth/register`.
- Таблицы: `registration_tokens` (read active), `users` (insert).
- Логика: найти активный токен → нет/неактивен → `403`; argon2id-хэш пароля; insert; занятый username → `409`.
- Приёмка: FR A1; §1 «Успешная регистрация по валидному токену», «Регистрация без токена запрещена».
- Тесты: успех; пустой/неверный токен→403; дубль username→409.
- Доки: godoc + бизнес-комментарий «почему закрытый доступ».

#### 1.3 — Логин / refresh / logout · M · deps: 1.1
- Эндпоинты: `POST /auth/login`, `/auth/refresh`, `/auth/logout`.
- Таблицы: `users` (verify), `refresh_tokens` (insert/rotate/revoke).
- Логика: login → проверка argon2id → access-JWT (TTL 15м, `JWT_SIGNING_KEY`) + непрозрачный refresh (хранить `token_hash`). refresh → найти по хэшу, не revoked/не истёк → новая пара, старый revoked. logout → revoked=true.
- Приёмка: FR A3.
- Тесты: ротация refresh; revoked→401; истёкший access→401; неверные креды→401.

#### 1.4 — Middleware auth · S · deps: 1.3
- Логика: парс `Authorization: Bearer`, валидация подписи/срока, `user_id` в контекст; иначе `401`.
- Приёмка: FR A3, D2; §1 «Доступ к API по токену».
- Тесты: валидный/протухший/битый токен.

#### 1.5 — Изоляция данных · M · deps: 1.4
- Логика: фильтр по `user_id` во всех запросах `tasks`/`integrations`; включить Postgres RLS (`user_id = current_setting('app.user_id')::uuid`), ставить `app.user_id` в начале транзакции (страховка).
- Приёмка: FR A4, I3; §1 «Изоляция данных между пользователями».
- Тесты: интеграционный — два юзера, перекрёстный доступ → пусто/404.

#### 1.6 — Показ токена регистрации · S · deps: 1.2
- Эндпоинт: `GET /admin/registration-token` (только `is_admin`, иначе `403`).
- Приёмка: FR A2; §1 «Администратор видит токен регистрации».
- Тесты: админ видит; не-админ→403.

#### 1.7 — Bootstrap · S · deps: 1.1
- Логика: CLI-команда оркестратора создаёт первого админа (из env) и стартовый токен (`INITIAL_REGISTRATION_TOKEN`).
- Приёмка: FR A2.
- Тесты: повторный bootstrap идемпотентен.

# EPIC 2 — Интеграции и UUID (FR B1–B6, Gherkin §2)

#### 2.1 — Схема интеграций · S · deps: 1.1
- Таблицы: `integrations` (миграция 00002 — подготовлена: `uuid_hmac`+`uuid_enc`).
- Тесты: миграция up/down.

#### 2.2 — CRUD + выдача UUID · M · deps: 2.1, 1.4
- Эндпоинты: `GET/POST /integrations`, `GET/PATCH /integrations/{id}`.
- Логика: создание — обязательное имя, опц. `ip_hint`; сгенерировать UUID, посчитать `uuid_hmac` (auth) и `uuid_enc` (AEAD, для показа); insert `status='offline'`; вернуть `IntegrationWithSecret`. GET — расшифровать `uuid_enc` и показать владельцу (нужен для настройки машины).
- Приёмка: FR B1, B2; §2 «Создание интеграции выдаёт UUID».
- Тесты: создание возвращает уникальный UUID; список — только свои.

#### 2.3 — Аутентификация машины по UUID · M · deps: 2.2
- Точка: WS-handshake `/machine/ws` (не REST).
- Логика: агент шлёт UUID → HMAC → поиск `uuid_hmac` → принять как интеграцию, если найдена и (`ip_hint` пуст ИЛИ совпал). Иначе `401`.
- Приёмка: FR B3, B6; §2 «Аутентификация машины по UUID», «IP — необязательная проверка».
- Тесты: валидный UUID; динамический IP при пустом hint; неверный UUID→401.

#### 2.4 — Защита от повторного UUID · S · deps: 2.3 — *ADR*
- Логика: одно активное WS-соединение на интеграцию; второй коннект → решить политику (закрыть старое / отвергнуть новое) и **записать ADR**; факт логировать.
- Приёмка: FR B6.
- Тесты: второй коннект обрабатывается по выбранной политике.

#### 2.5 — Редактирование не рвёт задачи · S · deps: 2.2, 5.4
- Эндпоинт: `PATCH /integrations/{id}`.
- Логика: меняет только `name`/`ip_hint`, активные задачи продолжаются.
- Приёмка: FR B5; §2 «Редактирование не рвёт активные задачи».
- Тесты: правка во время `running` — задача не падает.

#### 2.6 — Удаление с активными задачами · M · deps: 2.2, 8.4
- Эндпоинт: `DELETE /integrations/{id}?confirm=true`.
- Логика: есть активные задачи и нет confirm → `409`; при confirm — корректно отменить/завершить задачи через FSM, затем удалить.
- Приёмка: FR B5; §2 «Удаление интеграции требует подтверждения».
- Тесты: без confirm→409; с confirm — задачи закрыты, интеграция удалена.

#### 3.6 — Heartbeat и статус машины · M · deps: 3.2
- Логика: агент шлёт heartbeat в `machine.events`; оркестратор обновляет `last_seen_at`, ставит `offline` по таймауту (фоновый воркер).
- Приёмка: FR B4; §2 «Машина онлайн», «Машина оффлайн».
- Тесты: онлайн при свежем heartbeat; оффлайн по таймауту (асинхронно).

# EPIC 5 — Постановка задачи и FSM (FR E1–E7; Gherkin §4, §9)

#### 5.1 — Схема задач · M · deps: 1.1, 2.1

#### 5.2 — FSM · L · deps: 5.1
- Логика: таблица разрешённых переходов (map (status,event)→status); функция `Transition` — единственная точка смены статуса, пишет `task_events(status_change)` и `updated_at`; недопустимый переход → ошибка.

#### 5.3 — Постановка задачи · M · deps: 5.2, 3.2

- Таблицы: `tasks` (insert, `text_enc`), `task_events`.
- Логика: проверить владение интеграцией; insert `queued`; publish в `machine.commands` (ключ `task_id`); вернуть `Task`.

#### 5.4 — Доставка на машину · M · deps: 5.3, 3.4, 4.5
- Логика: мост доставил команду → агент принял → событие → `Transition` в `running`.
- Приёмка: FR E1; §4.
- Тесты: задача доходит до нужной машины и стартует.

#### 5.5 — Дедуп постановки · S · deps: 5.3
- Логика: уникальный индекс `(user_id, idempotency_key)`; повтор → вернуть существующую (`200`), не дублировать.
- Приёмка: FR E7; §4 «Защита от двойной отправки».
- Тесты: двойная отправка → одна задача.

#### 5.6 — Оффлайн-постановка · M · deps: 5.3, 3.5
- Логика: машина оффлайн → задача `queued`, команда в шине; при подключении мост дочитывает с offset и доставляет.
- Приёмка: FR E4; §9 «Задача поставлена при оффлайн-машине».

#### 5.7 — Таймаут «зависания» · M · deps: 5.4, 3.6
- Логика: воркер — нет heartbeat дольше порога (решение F2) → `Transition` в `stale` + событие-уведомление; возврат машины → `stale → running`.
- Приёмка: FR E5; §9 «Машина пропала надолго».
- Тесты: пропажа машины → stale + уведомление; возврат → продолжение.

#### 5.8 — Ошибки агента/машины · S · deps: 5.4
- Логика: событие ошибки → `Transition` в `failed` + `task_events(error)`.
- Приёмка: FR E1.
- Тесты: ошибка агента → failed.

#### 6.1 — Вопрос/ответ · M · deps: 5.2, 3.4
- Эндпоинт: `POST /tasks/{id}/answer`.
- Логика: агент задал вопрос → `task_events(agent_question)` → `Transition` в `waiting_user`; ответ пользователя (`ref_event_id`=вопрос) → `Transition` в `running`.
- Приёмка: FR F1; §5 «Агент задаёт вопрос и получает ответ».
- Тесты: вопрос→waiting_user; ответ→running.

#### 6.2 — Очередь нескольких вопросов · M · deps: 6.1
- Логика: ответ привязывается к конкретному `question_id` через `ref_event_id`.
- Приёмка: FR F2; §5 «Несколько вопросов сопоставляются корректно».
- Тесты: ответ на второй вопрос привязан именно к нему.

#### 6.3 — Allowlist · M · deps: 4.5
- Логика: команда из allowlist выполняется агентом без вопроса (дефолтный allowlist — решение F1 из ручного файла).
- Приёмка: FR F3; §5 «Команда из allowlist выполняется без вопроса».
- Тесты: allowlisted команда не уходит на согласование.

#### 6.4 — Согласование команды вне allowlist · M · deps: 6.3, 6.1
- Эндпоинт: `POST /tasks/{id}/approve`.
- Логика: команда вне allowlist → `command_approval_request` → `waiting_user`; не выполняется без `approve`.
- Приёмка: FR F3; §5 «Команда вне allowlist требует согласования».
- Тесты: до approve команда не выполнена.

#### 6.5 — Отклонение команды · S · deps: 6.4
- Логика: `decision=reject` → команда не выполняется, агент действует с учётом отказа.
- Приёмка: FR F3; §5 «Отклонение команды».
- Тесты: reject → команда не выполнена, агент продолжил.

#### 6.6 — Аудит решений · S · deps: 6.1
- Логика: все действия агента и решения пользователя пишутся в `task_events` (аудит).
- Приёмка: FR F4.
- Тесты: каждое решение оставляет запись.

#### 6.7 — Таймаут ответа · M · deps: 6.1, 7.1
- Логика: нет ответа дольше порога → напоминание (уведомление) + настраиваемое поведение (ожидание/авто-отмена) — решение F2.
- Приёмка: FR F5.
- Тесты: по таймауту приходит напоминание; авто-поведение срабатывает.

# EPIC 8 — Завершение, отмена, история (FR E2, E6, H1–H3; Gherkin §7, §8, §10)

#### 8.1 — Агент сообщил о завершении · S · deps: 5.2
- Логика: событие `agent_completed` → `Transition` в `awaiting_confirm` (НЕ закрывает задачу).
- Приёмка: FR E2; §7 «Агент сообщил о завершении — задача ещё не закрыта».
- Тесты: статус awaiting_confirm, не completed.

#### 8.2 — Подтверждение завершения · S · deps: 8.1
- Эндпоинт: `POST /tasks/{id}/confirm`.
- Логика: `awaiting_confirm → completed` только этим действием.
- Приёмка: FR E2; §7 «Пользователь подтверждает завершение».
- Тесты: confirm → completed; из других статусов confirm запрещён.

#### 8.3 — Отклонение результата · S · deps: 8.1
- Эндпоинт: `POST /tasks/{id}/reject`.
- Логика: `awaiting_confirm → running` (доработка).
- Приёмка: FR E2; §7 «Пользователь отклоняет результат».
- Тесты: reject → running.

#### 8.4 — Отмена доходит до машины · M · deps: 5.4, 3.4
- Эндпоинт: `POST /tasks/{id}/cancel`.
- Логика: команда отмены гарантированно доставляется; агент останавливается; `Transition` в `cancelled`; статус во всех каналах.
- Приёмка: FR E6; §8 «Отмена доходит до машины».
- Тесты: отмена из любого активного статуса → cancelled.

#### 8.5 — Сохранность данных при отмене · M · deps: 8.4, 4.5
- Логика: при критической операции агент доводит её до безопасного состояния; пользователь предупреждён, что мгновенная остановка не гарантируется (определение «критической» — решение F3).
- Приёмка: FR E6; §8 «Приоритет сохранности данных при отмене».
- Тесты: отмена в середине критической операции → безопасное завершение + предупреждение.

#### 8.6 — Состав истории · M · deps: 5.1
- Эндпоинты: `GET /tasks`, `GET /tasks/{id}`, `GET /tasks/{id}/events`.
- Логика: запись задачи (интеграция, таймстемп, текст, статус, ответ) + ответы пользователя с привязкой к запросу.
- Приёмка: FR H1; §10 «Состав записи о задаче».
- Тесты: полный цикл → все поля присутствуют.

#### 8.7 — Бессрочное хранение · S · deps: 8.6
- Логика: авто-удаления нет; старые задачи доступны.
- Приёмка: FR I2; §10 «Бессрочное хранение».
- Тесты: «старая» задача доступна.

#### 8.8 — Действия из истории в web · M · deps: 8.2, 8.4, 9.4
- Логика: из истории в web — отменить / ответить / подтвердить завершение.
- Приёмка: FR H2; §10 «Действия из истории в web».
- Тесты: каждое действие доступно для активной задачи.

#### 8.9 — Семантика правки текста запроса · S · deps: 8.6
- Логика: правка текста в истории не перезапускает выполненную задачу; повтор — отдельное действие.
- Приёмка: FR H3.
- Тесты: правка не триггерит повторное выполнение.

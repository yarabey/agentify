# Бизнес-ТЗ: распределённая система agentic-разработки с оркестратором

> Документ описывает «что и зачем»: пользовательскую ценность, объём, функциональные и бизнес-требования, критерии приёмки.
> «Как» (архитектура, схемы данных, протоколы) — предмет отдельного технического проектирования на основе этого ТЗ.

---

## 1. Видение и проблема
Разработчики хотят делегировать рутинную и сложную работу ИИ-агентам, но привязаны к месту: агент живёт у терминала конкретной машины. Мы убираем эту привязку — даём **асинхронное управление агентами на любых машинах из любого канала**, с безопасным согласованием действий и полной историей.

## 2. Цели и метрики успеха
- **Time-to-first-task** (от регистрации до первой выполненной задачи) — целевой ориентир онбординга.
- **Доля вопросов агента, на которые пользователь ответил** (а не «потерял»). Прямой индикатор работы асинхронной модели.
- **Доля задач, доведённых до завершения** без зависаний.
- **Среднее время реакции** пользователя на вопрос агента.
- **Инциденты безопасности** (нежелательные/несогласованные действия агента) → стремимся к нулю.

## 3. Целевая аудитория
Технические пользователи, управляющие собственными машинами; на старте — закрытый круг по токену регистрации.

## 4. Глоссарий
- **Оркестратор** — центральный сервис: аутентификация, хранение, маршрутизация, история.
- **Машина разработки (интеграция)** — любая машина пользователя с запущенным агентом, подключённая к оркестратору; описывается интеграцией.
- **Канал** — источник ввода пользователя (web-PWA, Telegram-бот, …), работающий через единый API.
- **Задача (запрос)** — сформулированная пользователем работа для агента.
- **Вопрос агента** — запрос решения/разрешения от агента к пользователю в ходе задачи.
- **Согласование действия** — частный случай вопроса: разрешить ли выполнить команду.

## 5. Объём: MVP против последующих фаз

**MVP (обязательно для запуска):**
- Регистрация по токену, логин, обновление токена, выход. Токен регистрации виден администратору в веб-интерфейсе.
- Один канал — web-PWA — полнофункциональный; Telegram как второй канал ввода и **уведомлений**.
- Создание/редактирование/удаление интеграции; выдача UUID.
- Однострочная установка агента на macOS и Ubuntu; провайдеры Claude и Claude Code. Провайдер/подписку настраивает сам пользователь при установке.
- Постановка задачи, цикл «вопрос-ответ», согласование команд по принципу **allowlist (как в Claude Code)**.
- **Уведомления** о вопросах агента: в web — через постоянное соединение (WebSocket), и в Telegram.
- Явный конечный автомат задачи с отменой и базовыми таймаутами. **Завершённой задачу делает только явное действие пользователя**; «агент сообщил о завершении» — отдельный промежуточный статус.
- **Все взаимодействия машина ↔ оркестратор — асинхронные через очередь сообщений**: оффлайн-сторона догоняет работу, когда снова онлайн.
- Индикатор статуса машины (онлайн/оффлайн) — асинхронно, через ту же очередь.
- История задач и ответов с изоляцией по пользователю; хранение бессрочное.

**Фаза 2:**
- Дополнительные провайдеры/агенты; несколько агентов на машине.
- Ротация/отзыв токена регистрации; квоты на параллельность как защита от перегруза.
- Расширенная модель разрешений (политики поверх allowlist), песочница.
- Web push-уведомления (помимо WebSocket); маршрутизация между несколькими активными каналами; email-фолбэк.
- Аудит-журнал, прогресс долгих задач.
- **Мягкие напоминания** о задачах в статусе «ожидает подтверждения» (агент отчитался, пользователь долго не подтверждает) — без авто-закрытия.

**Фаза 3+:**
- Новые каналы (другие мессенджеры, IDE-плагины, CLI).
- Командная работа, роли, общий доступ к интеграциям.
- Восстановление пароля/MFA, корпоративные политики.
- Открытие платформы за пределы закрытого круга (если продукт окажется удобным).

## 6. Функциональные требования

**A. Доступ и аккаунты**
- A1. Регистрация доступна только при предъявлении секретного токена.
- A2. Секретный токен регистрации виден администратору в веб-интерфейсе. Утечка токена не считается критичным риском. Ротация и отзыв токена — *(post-MVP)*.
- A3. Логин выдаёт токен доступа; поддерживается обновление и выход (отзыв).
- A4. Каждый пользователь видит и редактирует только свои данные; межпользовательская изоляция гарантируется.
- A5. *(Фаза 2+)* Восстановление пароля.

**B. Интеграции и машины**
- B1. Пользователь создаёт интеграцию: обязательное название, опциональный IP-«хинт».
- B2. Система выдаёт уникальный UUID; UUID трактуется как **секрет**, доступен пользователю. Ротация/отзыв UUID — *(post-MVP)*.
- B3. Аутентификация машины строится на UUID; IP — необязательная дополнительная проверка, отключаемая для машин с динамическим адресом.
- B4. Машина асинхронно сообщает о себе через очередь сообщений; UI показывает её статус (онлайн/оффлайн/последняя активность). Статус не требует прямого синхронного соединения.
- B5. Редактирование названия/IP не прерывает идущие задачи. Удаление интеграции с активными задачами требует подтверждения и корректно их завершает/отменяет.
- B6. Один UUID соответствует одной машине; повторное использование выявляется и блокируется.

**C. Подключение машины (установочный скрипт)**
- C1. Установка одной командой на macOS и Ubuntu.
- C2. Интерактивная фаза настройки спрашивает всё необходимое (адрес оркестратора, UUID, провайдеры, креды), затем агент работает в фоне как демон.
- C3. Поддержка нескольких агентов/провайдеров (на старте Claude и Claude Code).
- C4. Креды провайдеров хранятся на машине безопасно; в оркестратор не передаются без необходимости.
- C5. Политика автозапуска и перезапуска при сбое; механизм обновления с контролем совместимости версий.

**D. Каналы**
- D1. Единый API для всех каналов: логин, постановка/отмена задачи, ответ на вопрос.
- D2. Пользователь определяется по токену доступа.
- D3. Привязка канала к аккаунту описана явно (для Telegram — понятный флоу связывания).
- D4. Новые каналы добавляются через код, переиспользуя единый API, без изменения ядра.

**E. Жизненный цикл задачи**
- E1. Явный набор статусов: создана → в очереди → отправлена на машину → выполняется → ожидает ответа пользователя → продолжена → **агент сообщил о завершении (ожидает подтверждения)** → **завершена** / провалена / отменена / истёк таймаут.
- E2. **Статус «завершена» проставляется только явным действием пользователя.** Сообщение агента «задача решена» переводит её лишь в промежуточный статус «ожидает подтверждения» — система не считает задачу закрытой автоматически.
- E3. **Все обмены машина ↔ оркестратор асинхронны через очередь сообщений.** Если сторона была оффлайн, она получает накопленные сообщения и продолжает работу после восстановления связи — ничего не теряется.
- E4. Если машина оффлайн в момент постановки — задача ставится в очередь и будет доставлена при подключении; пользователь видит это в статусе.
- E5. Если машина пропала надолго в процессе — задача помечается как «зависшая» по таймауту; пользователь уведомляется. После возврата машины работа может быть продолжена.
- E6. **Отмена** гарантированно доходит до машины и останавливает агента. Приоритет при отмене — **сохранность данных**: критическая/деструктивная операция доводится до безопасного состояния, пользователь предупреждён, что мгновенная остановка не гарантируется.
- E7. Защита от дублей: повторная отправка той же задачи не создаёт дубль.
- E8. *(Фаза 2+)* Прогресс долгих задач виден пользователю.

**F. Вопросы и согласование действий**
- F1. Агент может задать вопрос или запросить разрешение на команду в ходе задачи.
- F2. Несколько вопросов выстраиваются в понятную очередь; ответы сопоставляются с конкретным вопросом.
- F3. Согласование команд работает по принципу **allowlist, как в Claude Code**: разрешённые команды выполняются без вопросов, остальное требует явного согласования пользователя.
- F4. Все действия агента и решения пользователя фиксируются для аудита.
- F5. Если ответа нет дольше заданного срока — напоминание, затем настраиваемое поведение (ожидание/авто-отмена).

**G. Уведомления (критичное)**
- G1. О вопросе агента и важных изменениях статуса пользователь получает уведомление. В MVP: в web — через постоянное соединение (WebSocket), и в Telegram.
- G2. Если активны несколько каналов — определена маршрутизация (куда доставлять, нужно ли дублировать).
- G3. *(Фаза 2+)* Web push-уведомления (когда вкладка закрыта), email-фолбэк, пользовательские настройки уведомлений.

**H. История и контроль**
- H1. Хранится: по запросу — целевая интеграция, таймстемп, текст, статус, текстовый ответ; по ответу пользователя — таймстемп и связь с запросом.
- H2. История доступна в каждом канале на чтение; в web — на редактирование: отмена задачи (с остановкой на машине), ответ на вопрос и **явное подтверждение завершения**.
- H3. Семантика редактирования текста запроса в истории определена явно (например: правка не перезапускает уже выполненную задачу; повтор — отдельное действие).

**I. Безопасность и данные**
- I1. Чувствительные данные (тексты запросов/ответов, креды) защищены при хранении.
- I2. История хранится бессрочно; авто-удаление не предусмотрено. Пользовательское удаление своих данных — *(post-MVP)*.
- I3. Полная изоляция данных между пользователями (закрытый мультитенант).

**J. Стоимость и провайдеры**
- J1. Оплата токенов/подписки провайдера полностью на стороне пользователя; провайдер и способ развёртывания агента выбираются пользователем при установке скрипта.
- J2. Платформа не управляет бюджетами провайдера. Лимит на число параллельных задач допустим как защита от перегруза *(Фаза 2)*.

## 7. Нефункциональные / бизнес-ограничения
- **Все** взаимодействия оркестратора и машин — асинхронные через очередь сообщений в обе стороны; синхронного «живого» соединения между ними не требуется.
- Оффлайн-сторона (машина или оркестратор) догоняет накопленные сообщения после восстановления связи; незавершённая работа не теряется.
- Доставка сообщений устойчива к дублям и сбоям; порядок в рамках одной задачи сохраняется.
- Весь функционал покрыт автоматическими тестами (из исходного ТЗ).
- Технологический стек зафиксирован заказчиком (оркестратор и бот — Go, web — React/PWA, агент — Go/Node.js, БД — PostgreSQL, шина — Redpanda) и не является предметом данного документа.

## 8. Критерии приёмки (по ключевым сценариям)

**Регистрация и логин**
- Без валидного токена регистрация невозможна; просроченный/отозванный/исчерпанный токен отклоняется.
- После логина пользователь видит только свои интеграции, задачи и историю.

**Подключение машины**
- Одна команда на чистой macOS/Ubuntu доводит до работающего фонового агента, подключённого к оркестратору.
- В UI машина отображается как «онлайн» в пределах разумного времени после запуска.

**Постановка задачи и Q&A**
- Задача, поставленная из web и из Telegram, доходит до нужной машины и выполняется.
- Когда агент задаёт вопрос, пользователь **получает уведомление** (в web — по WebSocket, и в Telegram) и может ответить из любого активного канала; агент продолжает после ответа.
- Команда вне allowlist не выполняется без явного согласования пользователя.

**Завершение задачи**
- Сообщение агента «задача решена» переводит её в статус «ожидает подтверждения», но не закрывает.
- Задача считается завершённой только после явного подтверждения пользователем.

**Асинхронность**
- Задача, поставленная при оффлайн-машине, доставляется и выполняется после её подключения — без потери.
- Если оркестратор или машина временно недоступны, после восстановления связи накопленные сообщения обрабатываются, работа продолжается.

**Отмена**
- Отмена задачи останавливает агента на машине; статус корректно отражается во всех каналах.
- При отмене во время критической операции пользователь предупреждён о поведении системы.

**Надёжность**
- Повторная отправка/доставка не приводит к двойному выполнению.
- При оффлайн-машине задача не теряется, пользователь уведомлён.

## 9. Вне объёма (MVP)
- Несколько провайдеров сверх Claude/Claude Code; несколько агентов на машине.
- Командная работа, роли, общий доступ к интеграциям.
- Полноценная песочница агента, расширенные политики разрешений поверх allowlist.
- MFA, восстановление пароля, web push, email-уведомления.
- Ротация/отзыв токена регистрации и UUID; удаление пользователем своих данных.

## 10. Решения заказчика (зафиксировано)
1. **Модель развёртывания:** закрытый мультитенант, пока для себя; при удобстве — возможное открытие для других людей позже.
2. **Стоимость:** платит пользователь (токены/подписка), сам выбирает провайдера и способ развёртывания агента при установке скрипта. Платформа бюджеты не контролирует.
3. **Отмена при деструктивных операциях:** приоритет — **сохранность данных** (безопасное доведение критической операции важнее мгновенной остановки).
4. **Модель разрешений:** **allowlist, как в Claude Code**.
5. **Ретеншн истории:** хранить **бессрочно**, авто-удаление не делаем (post-MVP).
6. **Токен регистрации:** виден администратору в веб-интерфейсе; ротация — post-MVP, утечка не критична.

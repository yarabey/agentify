# protocol.md — протокол обмена машина ↔ оркестратор

> На этот документ ссылаются тикеты 3.2–3.6, 5.3–5.8, 6.x. Источник правды по форматам сообщений, ACK/offset-семантике и онлайн/оффлайн.
> Связанные требования: бизнес-ТЗ §7, §124–126, FR B3/B4/E3/E6/E7. Стек: Redpanda (бэкбон), WebSocket (кромка агента).

## 1. Два уровня транспорта
- **Бэкбон (внутри инфраструктуры): оркестратор ↔ Redpanda.** Долговечность, порядок, догон. Топики — §3.
- **Кромка (наружу): агент ↔ оркестратор по WebSocket.** Агент держит исходящее соединение (работает за NAT), аутентифицируется по UUID. Redpanda наружу не выставляется.

Надёжность живёт на **обоих концах**: Redpanda на сервере + локальный durable outbox на агенте (bbolt). WebSocket — только «живая труба».

## 2. Конверт сообщения
Любое сообщение в обе стороны — JSON со стабильным конвертом:
```json
{
  "message_id": "uuid",        // глобально уникален; основа дедупа
  "task_id": "uuid|null",      // null только для machine-level (hello/heartbeat)
  "integration_id": "uuid",
  "type": "string",            // см. §4
  "seq": 123,                  // порядковый номер в рамках task_id (монотонный)
  "ts": "RFC3339",
  "protocol_version": "1",     // для контроля совместимости (FR C5, тикет 4.7)
  "payload": { }               // зависит от type
}
```
Правила:
- **Дедуп** — по `message_id` (приёмник хранит обработанные id / полагается на offset + идемпотентное применение).
- **Порядок** — гарантируется в рамках одного `task_id`. На `machine.events` это обеспечивается ключом партиции `task_id`; на `machine.commands` ключ партиции — `integration_id`, что даёт более сильную гарантию (порядок всех команд машины) и сохраняет порядок внутри задачи как следствие — все команды задачи идут к одной интеграции (раскладка — §3, [ADR 0001](adr/0001-redpanda-topics.md)).
- **Идемпотентность** — повторное применение того же `message_id` не меняет состояние.

## 3. Топики Redpanda
| Топик | Направление | Ключ партиции | Содержимое |
|---|---|---|---|
| `machine.commands` | оркестратор → агент | `integration_id` | команды машине (assign/answer/decision/cancel) |
| `machine.events` | агент → оркестратор | `task_id` (или `integration_id` для heartbeat) | события агента/машины |
| `notifications.telegram` | оркестратор → бот | `user_id` | уведомления для доставки |

Раскладка зафиксирована в [ADR 0001](adr/0001-redpanda-topics.md):

- **Один топик на направление**, число партиций фиксировано для MVP с заделом
  (`machine.commands` = 6, `machine.events` = 6, `notifications.telegram` = 3).
- **Адресация команд конкретной машине:** один общий топик `machine.commands`,
  мост-оркестратор читает его и **фильтрует по `integration_id`**, пушит кадр в активное
  WS нужной машины. Если машина оффлайн — сообщение остаётся в топике (offset не
  коммитится), мост дочитывает его при реконнекте (FR E4; см. §6).
- **Ключи партиций:** `machine.commands` → `integration_id` (порядок команд в адрес одной
  машины; порядок в рамках задачи сохраняется как следствие — все команды задачи идут к
  одной интеграции, §126); `machine.events` → `task_id`, а для machine-level
  (`hello`/`heartbeat`, где `task_id = null`) → `integration_id`;
  `notifications.telegram` → `user_id`.
- **Ретеншн** (cleanup `delete`, не вечный — история бессрочна в БД, FR I2):
  `machine.commands` ~7 дней, `machine.events` ~14 дней, `notifications.telegram` ~3 дня.
  Конкретные значения и обоснование — в ADR 0001.

Имена топиков и ключей вынесены в Go-константы `internal/bus` (см. `topics.go`).

## 4. Типы сообщений

### Агент → оркестратор (`machine.events`)
| type | payload | смысл |
|---|---|---|
| `hello` | `{uuid, agent_version, providers[]}` | первый кадр после WS-коннекта; аутентификация по UUID (FR B3) |
| `heartbeat` | `{}` | живость машины; обновляет `last_seen_at` (FR B4) |
| `ack` | `{ack_message_id}` | подтверждение обработки команды (см. §5) |
| `task_accepted` | `{}` | задача принята в работу → FSM `running` |
| `agent_question` | `{question_id, text}` | вопрос пользователю → FSM `waiting_user` (FR F1) |
| `command_approval_request` | `{request_id, command, reason}` | команда вне allowlist → `waiting_user` (FR F3) |
| `agent_progress` | `{text}` | прогресс (история/аудит) |
| `agent_completed` | `{summary}` | агент отчитался → FSM `awaiting_confirm` (НЕ закрывает, FR E2) |
| `error` | `{code, message}` | ошибка → FSM `failed` |

### Оркестратор → агент (`machine.commands`)
| type | payload | смысл |
|---|---|---|
| `task_assigned` | `{text}` | поставить задачу (FR E1) |
| `user_answer` | `{question_id, text}` | ответ пользователя; агент продолжает (FR F2) |
| `command_decision` | `{request_id, decision: approve\|reject}` | решение по согласованию (FR F3) |
| `cancel` | `{}` | отмена; безопасная остановка, приоритет сохранности данных (FR E6) |
| `ping` | `{}` | проверка живости соединения |

## 5. ACK / offset / доставка (at-least-once)
Команды оркестратор → агент:
1. Мост читает команду из `machine.commands`, пушит в WS машины, **держит offset незакоммиченным**.
2. Агент применяет команду идемпотентно, пишет её в локальный outbox, отвечает `ack{ack_message_id}`.
3. Оркестратор получил `ack` → **коммитит offset**. Нет `ack` за таймаут / реконнект → переотправка (возможен дубль → агент гасит по `message_id`).

События агент → оркестратор:
1. Агент кладёт событие в локальный outbox (durable) → шлёт по WS.
2. Оркестратор применяет (FSM/история), отвечает `ack`.
3. Агент получил `ack` → удаляет из outbox. Нет `ack` (оркестратор упал) → реплей при следующем коннекте (FR E3, §125).

Итог: «ничего не теряется» при падении любой стороны; дубли безопасны; порядок в рамках задачи сохранён.

## 6. Онлайн / оффлайн (FR B4)
- Агент шлёт `heartbeat` каждые `HEARTBEAT_INTERVAL` (по умолчанию 15 c).
- Оркестратор: `last_seen_at` свежее `OFFLINE_THRESHOLD` (по умолч. 45 c) → `online`, иначе фоновый воркер ставит `offline`.
- Оффлайн-постановка (FR E4): команда лежит в `machine.commands`; при реконнекте мост дочитывает с последнего offset и доставляет.
- «Зависание» (FR E5, тикет 5.7): нет heartbeat дольше `STALE_THRESHOLD` (продуктовое решение, MANUAL_STEPS §4) при активной задаче → FSM `stale` + уведомление; возврат машины → `stale → running`.

## 7. Версионирование (FR C5, тикет 4.7)
- `protocol_version` в каждом конверте.
- На `hello` оркестратор сверяет `agent_version`/`protocol_version`; несовместимые — отклоняет с понятной ошибкой (жёстко vs мягко — ADR 4.7).
- Несовместимые изменения протокола → инкремент версии + запись в `docs/adr/`.

## 8. Безопасность
- WS только поверх TLS (Caddy).
- UUID в `hello` сверяется по HMAC (`integrations.uuid_hmac`); опциональная проверка IP по `ip_hint` (FR B3).
- Креды провайдера в сообщениях **не передаются** (FR C4, J1).
- Тексты задач/ответов шифруются at-rest на стороне оркестратора (FR I1); в шине — внутри инфраструктуры.

# 0004. Мягкое удаление интеграции (soft-delete через `deleted_at`)

- **Status:** Accepted
- **Date:** 2026-07-01

> Тикет 2.6 (EPIC 2), зависит от 2.2, 8.4. Реализует FR B5 («Удаление интеграции с
> активными задачами требует подтверждения и корректно их завершает/отменяет») и
> Gherkin §2 «Удаление интеграции с активной задачей требует подтверждения».

## Контекст

Тикет 2.6 требует эндпоинт `DELETE /integrations/{id}?confirm=true`: без активных
задач — просто удалить; с активными задачами без `confirm` — `409`; с
`confirm=true` — корректно отменить/завершить задачи через FSM, затем удалить
интеграцию.

«Удалить» на первый взгляд читается как физический `DELETE FROM integrations`. Но
схема (`orchestrator/migrations/00003_tasks_and_events.sql:12`) объявляет:

```sql
integration_id UUID NOT NULL REFERENCES integrations(id) ON DELETE RESTRICT,
```

`ON DELETE RESTRICT` означает, что Postgres откажет в удалении строки `integrations`,
пока на неё ссылается хотя бы одна строка `tasks` — а по FR I2 («История хранится
бессрочно; авто-удаление не предусмотрено») строки `tasks`/`task_events` в MVP
никогда не удаляются. Таким образом, физический `DELETE FROM integrations WHERE
id=...` упал бы на FK-ограничении у **любой** интеграции, у которой хоть раз была
создана задача — даже полностью завершённая (`completed`/`cancelled`/`failed`), не
только у интеграции с активными задачами прямо сейчас. Отмена/завершение активных
задач (что явно требует сам тикет 2.6) эту проблему не решает: терминальный статус
задачи не убирает саму строку `tasks`, а FK ссылается на строку, а не на статус.

Это архитектурная развилка между двумя требованиями ТЗ («интеграцию можно удалить»
против «история задач хранится вечно»), которую сам тикет 2.6 не разрешает — нужно
явное решение, задокументированное отдельно от кода (см. прецеденты
[ADR 0001](0001-redpanda-topics.md), [ADR 0002](0002-machine-ws-duplicate-uuid-policy.md)).

Дополнительное требование безопасности: после удаления интеграция должна вести себя
как несуществующая везде, включая путь аутентификации машины на WS-handshake
(`GetIntegrationByUUIDHMAC`, тикет 2.3) — иначе удалённая интеграция могла бы
«воскреснуть» и снова аутентифицировать машину предъявлением старого UUID-секрета.

## Решение

Удаление интеграции реализуется как **мягкое удаление** через новую колонку
`integrations.deleted_at TIMESTAMPTZ` (`NULL` = интеграция активна, ненулевое
значение = удалена, миграция `orchestrator/migrations/00006_integrations_soft_delete.sql`).

`DeleteIntegrationsId` (`orchestrator/internal/api/integrations.go`) не выполняет
физический `DELETE`: он лишь выставляет `deleted_at = now()` через новый запрос
`SoftDeleteIntegration` (owner-scoped, идемпотентно исключает повторное удаление уже
удалённой строки — повторный вызов получает `pgx.ErrNoRows`, что обработчик
трактует как 404). Строки `tasks`/`task_events`, ссылающиеся на удалённую
интеграцию, никак не меняются и продолжают существовать бессрочно (FR I2) — FK
`ON DELETE RESTRICT` (миграция 00003) остаётся нетронутым и никогда не
срабатывает, поскольку физического `DELETE` строки `integrations` не происходит.

Все owner-scoped запросы, через которые интеграция видна владельцу или используется
для постановки задач (`ListIntegrationsByUser`, `GetIntegrationByIDAndUser`,
`UpdateIntegration` — `orchestrator/queries/integrations.sql`), дополнительно
фильтруют `AND deleted_at IS NULL`: удалённая интеграция не в списке, недоступна по
`GET/PATCH /integrations/{id}` (единый 404, тот же приём, что и для чужой/
несуществующей интеграции), и `POST /tasks` на неё тоже отвечает 404 (тот же
`GetIntegrationByIDAndUser`, `orchestrator/internal/api/tasks.go`).

Критично для безопасности: `GetIntegrationByUUIDHMAC` — путь аутентификации машины
на WS-handshake (тикет 2.3) — тоже дополнительно фильтрует `deleted_at IS NULL`.
Это гарантирует, что удалённая интеграция не может пройти WS-аутентификацию и
«восстать» повторным предъявлением своего UUID-секрета.

`uuid_hmac UNIQUE` (миграция `00002_integrations.sql`) остаётся как есть без
изменений. Повторное создание интеграции с тем же (уже физически невозможным
из-за случайной 128-битной генерации) UUID-секретом, что был у удалённой
интеграции, — не проблема этого тикета и не рассматривается.

## Альтернативы

- **Физический `DELETE` + ручное каскадное удаление `tasks`/`task_events`.**
  Отвергнуто: прямо противоречит FR I2 («история хранится бессрочно; авто-удаление
  не предусмотрено») — удаление истории задач при удалении интеграции стёрло бы
  именно ту историю, бессрочность которой явно требует ТЗ, и сломало бы будущие
  тикеты 8.x про историю/аудит.
- **Физический `DELETE`, но только когда у интеграции нет НИ ОДНОЙ задачи вообще
  (ни активной, ни исторической).** Отвергнуто: не решает основной кейс самого
  тикета 2.6 — «удаление интеграции С активными задачами» — сама постановка
  тикета предполагает, что у интеграции есть хотя бы одна задача прямо сейчас.
  На практике любая мало-мальски использованная интеграция имеет историю задач,
  так что этот вариант выродился бы почти всегда либо в `409` без реального пути
  вперёд, либо в `500` на FK-нарушении при попытке всё же удалить.
- **`tasks.integration_id` nullable + `ON DELETE SET NULL`.** Отвергнуто: при
  физическом удалении интеграции существующие задачи потеряли бы привязку к
  машине, на которой выполнялись — это ломает историю/аудит (FR H1, F4) и будущие
  тикеты 8.x, которым нужна привязка исторической задачи к конкретной интеграции
  (например, показ «какая машина выполняла эту задачу» в истории).

## Последствия

- **Плюсы:**
  - Не нарушает `ON DELETE RESTRICT` (миграция 00003) и не противоречит FR I2 —
    вся история задач удалённой интеграции сохраняется бессрочно, как и для любой
    другой интеграции.
  - `GET/PATCH /integrations/{id}` и `POST /tasks` на удалённую интеграцию
    корректно отвечают единым 404 благодаря общему owner-scoped фильтру в
    `GetIntegrationByIDAndUser` — отдельная ветка кода не нужна.
  - Удалённая интеграция не может аутентифицировать машину повторным
    предъявлением UUID-секрета (`GetIntegrationByUUIDHMAC` тоже фильтрует
    `deleted_at IS NULL`) — закрывает потенциальную дыру безопасности.
  - Минимальное изменение схемы (одна nullable-колонка, без каскадных операций).
- **Минусы / цена:**
  - `uuid_hmac UNIQUE` не снят: теоретически нельзя создать НОВУЮ интеграцию с тем
    же значением `uuid_hmac`, что было у удалённой (на практике недостижимо —
    UUID-секрет генерируется криптостойким `uuid.NewRandom`, коллизия статистически
    ничтожна; тот же аргумент уже принят в `PostIntegrations`, см.
    `orchestrator/internal/api/integrations.go`). Осознанно вне рамок тикета 2.6.
  - Строки `integrations` удалённых интеграций накапливаются в таблице бессрочно
    (как и `tasks`/`task_events`) — не решается этим ADR, согласуется с общей
    политикой FR I2.
- **Дальнейшие шаги:**
  - Будущие тикеты про историю/аудит (8.x) могут захотеть явно показывать
    «интеграция удалена» в истории задачи, ссылаясь на `deleted_at` — этот ADR
    закладывает для этого колонку, но не реализует такой UI/API.

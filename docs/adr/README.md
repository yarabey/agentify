# Architecture Decision Records (ADR)

Здесь живут **архитектурные решения** проекта — короткие записи о значимых развилках
(выбор библиотеки, формат протокола, схема топиков шины, модель auth и т.п.).
Правило из [AGENTS.md §5](../../AGENTS.md): любое значимое решение фиксируется ADR.

## Зачем
ADR делает выбор воспроизводимым: видно **контекст**, **что решили**, **что отвергли**
и **какой ценой**. Это защищает от повторного обсуждения уже закрытых вопросов и даёт
новым участникам (людям и агентам) быстрый ввод в историю архитектуры.

## Когда заводить ADR
- Выбор технологии/библиотеки, влияющий на несколько компонентов.
- Формат протокола шины, схема топиков, контракты межсервисного взаимодействия.
- Модель аутентификации/авторизации, изоляции данных.
- Любое решение, которое дорого откатить или о котором будут спрашивать «почему так».

> Инфраструктура доков (этот каталог, `make docs-check`, глоссарий) — **не**
> арх-развилка и ADR не требует.

## Как добавить ADR
1. Возьми следующий свободный **четырёхзначный** номер по порядку
   (`0000-template.md` — шаблон, не решение; первое реальное решение — `0001-*`).
2. Скопируй шаблон:
   ```bash
   cp docs/adr/0000-template.md docs/adr/0001-kratkiy-zagolovok.md
   ```
3. Имя файла — `NNNN-краткий-заголовок-через-дефис.md` (латиница/цифры/дефисы).
4. Заполни разделы **Контекст → Решение → Альтернативы → Последствия** и поля
   `Status` / `Date`. Структуру разделов не меняй.
5. ADR коммить вместе с изменением, которое он описывает (правило одного PR, §4).

## Статусы
- `Proposed` — предложено, обсуждается.
- `Accepted` — принято и действует.
- `Deprecated` — больше не актуально.
- `Superseded by ADR-NNNN` — заменено другим решением (укажи каким).

Принятые ADR **не редактируем по сути** — вместо правки заводим новый ADR, который
заменяет старый (меняем статус старого на `Superseded by ADR-NNNN`).

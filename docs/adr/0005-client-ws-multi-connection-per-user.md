# 0005. Несколько WS-соединений браузера на одного пользователя

- **Status:** Accepted
- **Date:** 2026-07-01

> Тикет 7.2 (EPIC 7), зависит от 7.1, 9.1. Реализует FR G1, §6 «Уведомление в web по
> WebSocket». Симметричен по постановке вопроса [ADR 0002](0002-machine-ws-duplicate-uuid-policy.md)
> (политика повторного WS-коннекта на стороне машины), но приходит к противоположному
> решению — см. «Контекст» ниже, почему аналогия не переносится буквально.

## Контекст

Тикет 7.2 добавляет клиентский WS-эндпоинт `/ws`: открытая вкладка браузера
аутентифицируется access-токеном (тот же JWT, что и REST API, `auth.ParseAccessToken`) и
получает push-уведомления (`notify.Notification`, тикет 7.1) без перезагрузки страницы.

`/machine/ws` (тикет 2.3/2.4) уже решает похожий по форме вопрос — реестр активных
WS-соединений, ключ вида `X → *websocket.Conn` — и там принята политика «одно соединение
на ключ, новое вытесняет старое» (ADR 0002). Нужно решить: применима ли та же политика к
клиентскому WS, или ключевое отличие в природе ключа требует другой архитектуры.

Различие в природе `integration_id` и `user_id` как ключей реестра:

- `integration_id` идентифицирует ОДНУ машину (один демон-агент на одной физической
  машине пользователя, тикет 2.2). Два одновременных WS одной интеграции — это по
  протоколу (`docs/protocol.md` §3) один и тот же логический получатель команд; двух
  одновременно живых получателей одной интеграции протокол не предусматривает, отсюда и
  вытеснение (ADR 0002).
- `user_id` идентифицирует ЧЕЛОВЕКА, а не устройство или вкладку. Один и тот же человек
  рутинно держит НЕСКОЛЬКО одновременно открытых вкладок/окон браузера (несколько
  мониторов, ноутбук + рабочий комп, вкладка авторизована ранее и не закрыта) — это не
  edge case и не подозрительная ситуация, а нормальный сценарий использования PWA
  (`docs/01_tech_stack_and_architecture.md`, "Web push в MVP вне объёма... уведомления в
  web — только по WebSocket при открытой вкладке": именно "вкладке", не "сессии").
- Приёмочное требование тикета (FR G1, §6, Gherkin «Дано у меня открыт веб-интерфейс /
  Когда агент задаёт вопрос... / Тогда я вижу уведомление в web без перезагрузки») не
  уточняет, какая именно вкладка; естественное прочтение — ЛЮБАЯ открытая вкладка этого
  пользователя должна увидеть уведомление, а не только «последняя».
- В отличие от `/machine/ws`, у клиентского канала нет обратной адресации команд
  (`docs/protocol.md` §3 не применим к web) — здесь только один поток "сервер → браузер",
  доставка одного и того же уведомления нескольким получателям не создаёт двусмысленности
  в духе at-least-once/ACK-семантики моста (тикет 3.4), которая и была одним из аргументов
  ADR 0002 против множественных соединений на стороне машины.

## Решение

**Реестр клиентских WS-соединений допускает НЕСКОЛЬКО одновременных соединений на одного
`user_id`, и уведомление рассылается ВСЕМ им.** В отличие от `Server.machineConns
map[integration_id]*websocket.Conn` (ADR 0002), клиентский реестр —
`ClientConnHub.conns map[uuid.UUID]map[*websocket.Conn]struct{}`
(`orchestrator/internal/api/client_ws.go`): на каждый `user_id` — МНОЖЕСТВО соединений, а
не одно.

- При успешной аутентификации (`GetWs` → `authenticateClientWS`) новое соединение
  ДОБАВЛЯЕТСЯ в набор `user_id`, не вытесняя уже открытые — все они остаются активными
  одновременно.
- `ClientConnHub.Notify` (реализует `api.Notifier`, тикет 7.1) находит набор соединений
  для `n.UserID` и пишет кадр уведомления КАЖДОМУ из них независимо; ошибка записи в одно
  соединение не прерывает рассылку остальным (по аналогии с тем, как ack одной интеграции
  в `machine_ws.go` не блокирует обработку других — но здесь это ещё и прямое следствие
  решения "разослать всем").
- При дисконнекте соединение удаляется ИЗ НАБОРА (не из всего реестра пользователя);
  пустой набор удаляется целиком, чтобы реестр не рос бесгранично простаивающими пустыми
  записями (аналог compare-and-delete ADR 0002, но здесь — просто delete из map конкретной
  записи набора, без гонки "session takeover": разные соединения одного пользователя не
  конкурируют за один слот).
- Отсутствие открытых соединений для `user_id` — НЕ ошибка `Notify` (возвращает `nil`):
  пользователь просто не в сети ни в одной вкладке, доставка "потеряна" в духе best-effort
  (см. «Последствия» — то же ограничение принято явно, ниже).

## Альтернативы

- **Применить политику ADR 0002 буквально («одна вкладка на пользователя, новая
  вытесняет старую»).** Отвергнут: рвал бы штатный сценарий работы с несколькими
  вкладками/окнами — открытие новой вкладки `/tasks` молча обрывало бы WS в старой,
  которая продолжает казаться пользователю рабочей, но перестаёт получать уведомления без
  какого-либо видимого сигнала (в отличие от агента, у пользователя нет auto-reconnect
  UI-цикла, который бы это заметил и переподключился). Аргумент ADR 0002 «на ключ — не
  более одного маршрутизируемого получателя» здесь не действует: у клиентского канала нет
  обратной адресации команд, которая требовала бы однозначности получателя.
- **Один процесс — одно соединение на пользователя, но реализовать поверх reference
  counting/переключения на «последнюю активную» вкладку (аналог фокуса окна).** Отвергнут
  как ненужное усложнение для MVP: потребовал бы протокола между вкладками (BroadcastChannel
  API и т.п.) для согласования "кто активен", тогда как рассылка всем тривиальна и
  полностью закрывает приёмочное требование («уведомление в открытой вкладке»,
  без уточнения какой).
- **Распределённый реестр (Redis pub/sub и т.п.) для будущей multi-instance топологии.**
  Отвергнут по тем же причинам, что и в ADR 0002: один процесс оркестратора в MVP
  (`docs/01_tech_stack_and_architecture.md` [РЕШЕНИЕ 5]) делает in-memory реестр
  достаточным; распределённая координация — кандидат на пересмотр при горизонтальном
  масштабировании.

## Последствия

- **Плюсы:**
  - Пользователь с несколькими открытыми вкладками видит уведомление в КАЖДОЙ из них —
    соответствует естественному прочтению приёмки тикета и Gherkin-сценария.
  - Реестр и `Notify` не имеют скрытых побочных эффектов на другие вкладки того же
    пользователя (в отличие от вытеснения ADR 0002, здесь открытие новой вкладки НИКОГДА
    не рвёт уже работающие).
  - Модель проще в реализации, чем reference counting/межвкладочная координация:
    `map[user_id]map[*Conn]struct{}` под одним мьютексом, без гонок session-takeover
    (разные соединения одного пользователя не претендуют на один слот реестра).
- **Минусы / цена:**
  - При множестве открытых вкладок одно уведомление физически отправляется N раз (по
    числу вкладок) — незначительная избыточность трафика, приемлемая для MVP (уведомления
    редки и малы, не поток данных).
  - Если ВСЕ вкладки пользователя закрыты в момент `Notify` — уведомление безвозвратно
    теряется (`Notify` возвращает `nil`, не ошибку): в MVP нет персистентной истории
    непрочитанных web-уведомлений (это НЕ входит в объём тикета 7.2 — история/read-статус
    оставлены будущим тикетам 9.4/9.5, если будут). Пользователь без открытой вкладки в
    момент вопроса агента не узнает об этом через web-канал вовсе — это ограничение и
    архитектуры in-memory реестра, и текущего решения продукта (docs/MVP_TICKETS.md не
    требует персистентной доставки для 7.2, а Telegram-канал 7.3 — отдельный, надёжный
    путь для того же события).
- **Дальнейшие шаги:**
  - Реестр `ClientConnHub`, заведённый этим тикетом, естественно переиспользуется тикетом
    6.7 (`task.AnswerTimeoutWorker`, напоминание `KindAnswerReminder`) как тот же `Notifier`
    — единая точка доставки web-уведомлений обоих видов.
  - Персистентная история/read-статус уведомлений, если понадобятся продукту, — предмет
    отдельного будущего тикета/ADR, не переиспользующего чисто in-memory `ClientConnHub`
    как единственный источник истины.

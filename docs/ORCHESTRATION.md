# ORCHESTRATION.md — как ведётся разработка

> Модель исполнения: **один оркестрирующий агент** ведёт цикл и на **каждый тикет порождает отдельного субагента**. Состояние прогресса хранится в `main` в `docs/PROGRESS.md` и читается перед каждым тикетом — чтобы перезапуск не начинал всё заново.

## 1. Источники правды
- **Что делать:** `docs/MVP_TICKETS.md` (тикеты, deps, последовательность).
- **Что уже сделано:** `docs/PROGRESS.md` — **только то, что в `main`** (= смёржено). Источник истины о готовности.
- **Как делать:** `AGENTS.md` (DoD, документация), `api/openapi.yaml`, `orchestrator/migrations/`, `docs/protocol.md`, `docs/Жизненный цикл задачи.md`, `docs/User_stories_Gherkin.md`.

## 2. Цикл оркестратора
Повторять до тех пор, пока остались не-`done` тикеты:
1. **`git checkout main && git pull`** — взять свежий `main`.
2. **Прочитать `docs/PROGRESS.md`** из `main`. Готовыми считать только `done`.
3. **Выбрать следующий тикет**: первый по порядку из `MVP_TICKETS.md`, у которого все `deps` уже `done` и сам он не `done`/`in_progress`. Учитывать спринты и критический путь.
4. **Отметить `in_progress`** в `PROGRESS.md` (коммит прямо в `main`) — чтобы параллельные/повторные запуски не взяли тот же тикет.
5. **Породить субагента** строго на этот один тикет (бриф — §4). Дать ему ID тикета и список файлов-контекста.
6. Субагент создаёт **ветку `ticket/<ID>`**, реализует тикет, открывает PR.
7. **Проверить DoD** (зелёные `make lint test bdd docs-check`, обновлены доки и `openapi.yaml` при изменении API, есть ADR где требуется). Если нет — вернуть субагенту на доработку.
8. **Смёржить PR в `main`.**
9. **Обновить `docs/PROGRESS.md` в `main`**: статус тикета → `done`, проставить PR и дату. **Это единственный писатель PROGRESS — сам оркестратор** (исключает конфликты).
10. Вернуться к шагу 1.

> Параллельность допустима, но writer у `PROGRESS.md` один (оркестратор). Если запускаешь несколько субагентов сразу — бери только тикеты с непересекающимися файлами и уже `done` зависимостями.

## 3. Поведение при перезапуске
- Всегда стартуй с шагов 1–2: `main` + `PROGRESS.md` — единственная истина.
- `done` — пропускаешь.
- `in_progress` — проверь, есть ли смёрженный PR: если да → пометь `done`; если PR открыт → доведи и смёржь; если ничего нет → начни тикет заново (предыдущая попытка не дошла до `main`, значит её нет).
- Никогда не доверяй памяти/локальному состоянию вне `main`.

## 4. Бриф субагенту (шаблон, который выдаёт оркестратор)
```
Ты реализуешь РОВНО ОДИН тикет: <ID> из docs/MVP_TICKETS.md. Не выходи за его рамки.
Сначала прочитай: AGENTS.md, блок тикета <ID> в MVP_TICKETS.md и его зависимости,
плюс относящиеся файлы (api/openapi.yaml, migrations/, docs/protocol.md,
docs/Жизненный цикл задачи.md, docs/User_stories_Gherkin.md).

Сделай:
1. git checkout main && git pull && git checkout -b ticket/<ID>
2. Реализуй блок «Логика». Закрой «Приёмку» тестами (unit + integration на testcontainers
   + godog по указанным Gherkin-сценариям).
3. Соблюди DoD из AGENTS.md: документация тех+бизнес, trace-комментарии (FR…, Gherkin §…),
   обнови openapi.yaml при изменении API, ADR в docs/adr/ если тикет помечен *ADR*.
4. Прогон: make lint test bdd docs-check — всё зелёное.
5. Открой PR с заголовком "ticket/<ID>: <название>", в описании укажи ID, закрытые
   FR/Gherkin и что задокументировано.
НЕ трогай docs/PROGRESS.md — его ведёт оркестратор. Не делай фич вне MVP. Не коммить секреты.
Если спецификация реально блокирует и решение продуктовое — верни оркестратору один точный вопрос.
```

## 5. Формат `docs/PROGRESS.md`
Таблица со статусами `todo | in_progress | done | blocked`. Ведёт только оркестратор. Зависимости смотри в `MVP_TICKETS.md`. Пример строки:
```
| 1.2 | done | #14 | 2026-07-03 | регистрация по токену |
```

# internal/crypto — общий крипто-модуль приложения

## Назначение (бизнес)

Несколько таблиц БД хранят данные, которые не должны лежать в открытом виде
(FR I1, тикет 11.1; FR B2, тикеты 2.2/2.3): UUID-секрет интеграции, текст
задачи, содержимое событий. Этот пакет — **единственное** место в монорепо, где
выполняется симметричное шифрование и HMAC, чтобы все таблицы использовали одну
проверенную реализацию, а не россыпь самопальных шифрований по сервисам.

## Что предоставляет (тех)

- `Encrypt(key, plaintext) → nonce||ciphertext+tag` / `Decrypt(key, …)` —
  AEAD-шифрование **AES-256-GCM** (`crypto/aes` + `crypto/cipher`). Ключ — ровно
  32 байта (AES-256), иначе `ErrInvalidKeyLength`. Nonce случайный
  (`crypto/rand`), генерируется заново на каждый вызов и хранится в префиксе
  результата — переиспользование nonce с тем же ключом в GCM недопустимо,
  поэтому `Encrypt` никогда не принимает nonce снаружи.
- `HMACSHA256(key, data)` — детерминированный необратимый отпечаток для поиска
  секрета в БД без хранения/расшифровки (например, аутентификация машины по
  UUID, тикет 2.3).
- `DeriveKey(masterKey, purpose)` — вывод независимого 32-байтного подключа из
  мастер-ключа под конкретное назначение (HMAC-SHA256 как одна итерация
  HKDF-Expand).

Ключи **никогда** не генерируются и не дефолтятся внутри пакета — вызывающая
сторона передаёт их как `[]byte` (в проде — `APP_ENCRYPTION_KEY` из окружения,
см. [`docs/MANUAL_STEPS.md`](../../docs/MANUAL_STEPS.md)).

## Формат хранения

`nonce || ciphertext+tag` — стандартная самодостаточная упаковка для GCM: для
расшифровки достаточно того же ключа и этого среза целиком. Пустой/nil plaintext
корректно шифруется (результат непуст — nonce+tag) и расшифровывается обратно в
пустой срез.

## Обоснование ключевых решений (ADR-lite)

Тикет 11.1 не помечен как требующий ADR, но выбор нетривиален — фиксируем кратко:

- **AES-256-GCM, а не chacha20poly1305.** Оба допускались тикетом. Выбран
  AES-256-GCM: только стандартная библиотека Go (`crypto/aes`+`crypto/cipher`),
  без внешних зависимостей; AES-NI аппаратно ускорен на целевом x86-64 VPS.
  Свойства AEAD (конфиденциальность + аутентичность) идентичны для задачи.
- **`DeriveKey` вместо прямого использования мастер-ключа.** Один и тот же
  мастер-ключ не должен применяться напрямую сразу в `Encrypt` и в
  `HMACSHA256`, а также в разных зашифрованных колонках — это reuse ключа в
  разных примитивах/контекстах, плохая крипто-гигиена. Каждое применение
  выводит свой подключ под своей строкой `purpose` (например,
  `integration-uuid-aead`, `integration-uuid-hmac`, `task-text-aead`,
  `task-event-payload-aead`) — разные `purpose` дают статистически независимые
  подключи из одного мастер-ключа.
- **API не завязан на применение.** Сигнатуры оперируют `[]byte`, а не
  «integration»/«uuid»/«task» — это общий примитив, переиспользуемый разными
  таблицами и сервисами.

## Кто использует

- `orchestrator/internal/api` — `integrations.uuid_enc` (шифр+HMAC),
  `tasks.text_enc` (шифр на записи, расшифровка на чтении),
  `task_events.payload_enc` (расшифровка на чтении).
- `orchestrator/internal/task` — `task_events.payload_enc` (шифрование на
  записи, единственный писатель `Transitioner`).

Подробнее о раскладке колонок и согласовании подключей — раздел «Шифрование
at-rest» в [`orchestrator/README.md`](../../orchestrator/README.md).
